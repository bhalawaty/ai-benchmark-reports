00The cast

Three services, each with its own data stores. The golden rule of the whole design: the engine never touches a tenant database — it generates SQL and sends identity; the owning service (v2) validates, scopes, and executes.

AI Engine

Conversational layer (AR/EN). Classifies intent, generates SQL with an LLM, asks v2 to run it, summarizes the result, assembles the answer blocks (text / table / chart / file / redirect).

Python 3.12 · FastAPI · LangGraph · :8099
owns → PostgreSQL+pgvector :5433 (conversations, messages, audit, RAG vectors) · Redis :6380 (cache/quota)
external → LLM via OpenRouter→Gemini (testing only; in-KSA self-hosted planned) · embeddings local Ollama :11434

HR-MCP

Thin MCP server — the standard tool boundary between the engine and HR. Exposes 5 read-only tools and forwards each call to v2's internal API with its own service credentials. Stateless; no database.

Python · FastMCP (mcp 1.27) · Streamable HTTP · :9100
tools → get_schema · run_query · get_column_values · run_report · report_status
auth in → HS256 JWT (aud=hr-mcp) · auth out → X-Api-Key + identity headers

Backend-v2

The executor and data owner. Validates AI SQL through a multi-layer safety pipeline, executes read-only against the right tenant DB, builds the report files, signs the download links, queues the big jobs.

PHP 8.3 · Laravel 11 (AiChatAssistance + ReportsManagement) · :8004
owns → MySQL central + one DB per tenant (stancl/tenancy) · GCS (report files) · Redis queue (reports_v2)

02Request lifecycle — the main path

One question, the happy path. The engine understands the question, asks HR-MCP what it can query, writes the SQL, runs it through HR-MCP → backend-v2 (which executes read-only on the tenant DB), then summarizes the answer. The key rule: the engine never touches the tenant DB directly — every data call goes through HR-MCP. (Edge cases — injection refusal, out-of-scope chat, the SQL self-correction retry, and the sync-vs-async report split — are left out here; they live in the pipeline diagram in section 03.)

05Auth matrix — what credential crosses each hop

The chain has two identity gates. The engine's first gate (optional, IDENTITY_VALIDATION_ENABLED) validates the end-user token against IdentityCore before any work runs; Backend-v2 is the authoritative second gate downstream. Three distinct credentials travel the chain — keep the user token separate from the two service credentials.

HopCredentialCarries / proves
FE → Engine /chat/askBearer token + X-Workspace + X-User-Id (+ X-Locale)End-user identity & tenant; missing headers → 401
Engine → IdentityCore (1st gate · optional)gRPC IdentityService.WhoAmI — Bearer + x-workspace metadataValidates the token is active before the pipeline runs. Invalid → 401; IdentityCore unreachable → 503 (fail-closed). OFF by default; positive results cached (SHA-256 of token+workspace, 300s)
Engine → HR-MCPShort-lived HS256 JWT, aud=hr-mcpClaims: workspace + user_id — proves the engine to HR-MCP; the user’s own token is relayed alongside via X-Forwarded-Authorization (never the engine’s credential)
HR-MCP → v2 /internal/ai/* (2nd gate)X-Api-Key (HR-MCP’s own service key) + X-Workspace + relayed user tokenService-to-service trust; v2 resolves tenant from workspace and is the authoritative validator/authorizer
v2 → Tenant MySQLRead-only transaction · scoped SQLRow-level scope injected (team/user/access-scope) · 5s timeout · blocked-column denylist
FE → report file24h signed GCS URLRe-minted on every status call — never a long-lived link
Three credentials — don’t conflate them: the end-user token (Ory/IdentityCore) says who the user is — validated optionally at the engine, authoritatively at v2. The engine→HR-MCP JWT and the HR-MCP→v2 X-Api-Key are service credentials that prove each hop, not the user.
